# บทเรียน Level 30 — วิธีการ Troubleshoot อย่างเป็นระบบ (ฉบับละเอียด)

> อ่านจบแล้วจะ: มีกระบวนการแก้ปัญหาที่ใช้ได้กับทุกเคส · เลือกวิธีไล่ปัญหา (Bottom-up, Top-down, Divide & Conquer, Follow-the-path, Compare, Swap) ได้เหมาะสม · ถามคำถามคัดกรองถูก · สื่อสารระหว่างแก้ปัญหา · เขียน RCA แบบมืออาชีพ

---

## 1. ทำไมต้องมีวิธีการ

มือใหม่มักแก้ปัญหาแบบ "ลองเปลี่ยนนั่นนี่ไปเรื่อย ๆ" ซึ่ง
- **ช้า** และอาจโชคดีแก้ได้โดยไม่รู้สาเหตุ (ปัญหากลับมาอีก)
- **อันตราย** — เปลี่ยนหลายอย่างพร้อมกันจนสร้างปัญหาใหม่
- **อธิบายลูกค้า/หัวหน้าไม่ได้** ว่าเกิดอะไรขึ้น

วิศวกรที่เก่งใช้ **กระบวนการแบบวิทยาศาสตร์**: เก็บข้อมูล → ตั้งสมมติฐาน → ทดสอบทีละอย่าง → ยืนยัน → บันทึก

---

## 2. กระบวนการ 7 ขั้น

```
 ① นิยามปัญหา  →  ② เก็บข้อมูล  →  ③ วิเคราะห์/ตั้งสมมติฐาน  →  ④ ทดสอบสมมติฐาน
        ▲                                                            │
        │                 ไม่ใช่ ← ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┘ ใช่
        │                                                            ▼
 ⑦ บันทึก/สื่อสาร/RCA  ←  ⑥ ยืนยันว่าแก้แล้ว + ไม่มีผลข้างเคียง  ←  ⑤ แก้ไข (มีแผนย้อนกลับ)
```

### ① นิยามปัญหาให้ชัด
"เน็ตใช้ไม่ได้" ไม่ใช่นิยามที่ดี → ต้องได้ประโยคแบบ:
> "ผู้ใช้แผนกบัญชีชั้น 3 (ประมาณ 20 คน) เปิดระบบ ERP ไม่ได้ตั้งแต่ 09:10 น. ส่วนอีเมลและอินเทอร์เน็ตใช้ได้ปกติ แผนกอื่นใช้ ERP ได้"

### ② เก็บข้อมูล — คำถามคัดกรอง (สำคัญที่สุด)

| คำถาม | ทำไมสำคัญ |
|---|---|
| **อะไร** ใช้ไม่ได้? อาการ/ข้อความ error ตรง ๆ คืออะไร? | แยกว่าเป็นแอปเดียวหรือทั้งหมด |
| **ใคร** ได้รับผลกระทบ? คนเดียว/ทั้งแผนก/ทั้งตึก/ทุกคน? | ชี้ว่าปัญหาอยู่ที่เครื่อง หรือที่อุปกรณ์ที่ใช้ร่วมกัน |
| **ที่ไหน**? สาย/Wi-Fi? สาขาไหน? ทำงานจากบ้าน (VPN)? | จำกัดขอบเขตทางกายภาพ/เครือข่าย |
| **เมื่อไร** เริ่ม? ตลอดเวลาหรือเป็นช่วง ๆ? เวลาใดเป็นพิเศษ? | สัมพันธ์กับเหตุการณ์อื่น (backup, change, peak) |
| **มีอะไรเปลี่ยนแปลงล่าสุดบ้าง?** (change, update, ย้ายอุปกรณ์, เพิ่ม user) | **ปัญหาส่วนใหญ่เกิดจาก change** — คำถามที่สำคัญที่สุด |
| เคยใช้ได้ไหม? ทำอะไรไปแล้วบ้าง? | ไม่ทำซ้ำ และรู้ว่ามีใครแก้อะไรไปแล้ว |
| **ผลกระทบต่อธุรกิจ** คืออะไร? | กำหนดความเร่งด่วน (priority) |

**ข้อมูลทางเทคนิค:** monitoring/alert, log ของอุปกรณ์, ticket ก่อนหน้า, change calendar, topology, baseline

### ③ วิเคราะห์ / ตั้งสมมติฐาน
เรียงสาเหตุที่เป็นไปได้จาก **โอกาสสูงและตรวจง่าย** ไปหา **โอกาสต่ำและตรวจยาก**

### ④ ทดสอบทีละสมมติฐาน
- **เปลี่ยนทีละอย่าง** แล้วสังเกตผล
- เลือกการทดสอบที่ **ไม่ทำลาย** ก่อน (show, ping, capture) แล้วค่อยเปลี่ยนค่า

### ⑤ แก้ไข
- มี **แผนย้อนกลับ (rollback)** เสมอ
- ถ้ากระทบระบบอื่นหรือเป็นช่วงเวลาทำงาน ต้องขออนุมัติตามขั้นตอน change (เว้นแต่เป็น emergency)
- **กู้บริการก่อน (workaround) แล้วค่อยหา root cause** — แต่ถ้าทำได้ ให้เก็บหลักฐาน (log, show tech, capture) **ก่อน** reboot/แก้

### ⑥ ยืนยัน
- ให้ **ผู้ใช้ยืนยัน** ว่าใช้งานได้จริง (ไม่ใช่แค่ ping ผ่าน)
- ตรวจว่าไม่มีผลข้างเคียงกับระบบอื่น

### ⑦ บันทึกและสื่อสาร
ปิด ticket ด้วยสาเหตุ วิธีแก้ และสิ่งที่ควรทำต่อ, เขียน RCA เมื่อเป็นเหตุการณ์ใหญ่, ปรับปรุง KB/runbook

## 3. วิธีไล่ปัญหา (Troubleshooting Approaches)

### 3.1 Bottom-Up (ล่างขึ้นบน)
เริ่มที่ L1 (สาย, ไฟพอร์ต) แล้วขึ้นไปทีละชั้นตาม OSI
- ✅ ละเอียด ไม่พลาด เหมาะกับมือใหม่และปัญหาที่สงสัยฮาร์ดแวร์
- ❌ ช้า ถ้าปัญหาอยู่ชั้นบน

### 3.2 Top-Down (บนลงล่าง)
เริ่มที่แอปพลิเคชัน (L7) แล้วลงมา
- ✅ เหมาะเมื่อสงสัยแอป/ผู้ใช้คนเดียว
- ❌ ถ้าปัญหาอยู่ชั้นล่าง จะเสียเวลา

### 3.3 Divide and Conquer ⭐ (นิยมที่สุดเมื่อมีประสบการณ์)
เริ่มที่ **ชั้นกลาง** — มักเป็น **L3 ด้วย ping**
- ping ผ่าน → ชั้นล่างปกติ ไปดูชั้นบน (port, DNS, แอป)
- ping ไม่ผ่าน → ไล่ลงชั้นล่าง (ARP/VLAN/สาย)

### 3.4 Follow-the-Path (ตามเส้นทาง)
ไล่ตามทางที่ข้อมูลเดิน hop ต่อ hop: PC → access switch → distribution → firewall → server ตรวจทีละจุดด้วย traceroute, MAC table, route table, firewall log
- ✅ เหมาะกับปัญหาข้ามหลายอุปกรณ์

### 3.5 Compare Configurations (เทียบกับที่ใช้ได้)
เทียบกับอุปกรณ์/พอร์ต/ผู้ใช้ที่ทำงานปกติ หรือเทียบกับ config backup ก่อนเกิดปัญหา (`diff`)
- ✅ เร็วมาก เมื่อมีของที่ใช้ได้ให้เทียบ

### 3.6 Swap Components (สลับเปลี่ยน)
สลับสาย/พอร์ต/SFP/เครื่อง เพื่อดูว่าปัญหาย้ายตามหรือไม่
- ✅ แยกฮาร์ดแวร์เสียได้เร็ว
- ❌ ต้องไปหน้างาน และอาจไม่พบสาเหตุที่แท้จริง

### เลือกวิธีอย่างไร
| สถานการณ์ | วิธีที่เหมาะ |
|---|---|
| ผู้ใช้คนเดียว แอปเดียวมีปัญหา | Top-down |
| ทั้งพื้นที่ใช้ไม่ได้ / สงสัยฮาร์ดแวร์ | Bottom-up |
| ไม่แน่ใจเลย ต้องการผลเร็ว | Divide & Conquer (ping) |
| ปัญหาข้ามหลายอุปกรณ์/สาขา | Follow-the-path |
| เครื่องหนึ่งใช้ได้ อีกเครื่องใช้ไม่ได้ | Compare |
| สงสัยสาย/SFP/พอร์ตเสีย | Swap |

## 4. Baseline — รู้ว่า "ปกติ" เป็นอย่างไร

ถ้าไม่รู้ว่าปกติ CPU ของ core switch อยู่ที่ 20% ก็ตัดสินไม่ได้ว่า 60% ผิดปกติหรือไม่
- เก็บ **baseline**: bandwidth, CPU/memory, latency, จำนวน error, จำนวน user ในช่วงเวลาปกติ
- ใช้ระบบ monitoring เก็บข้อมูลย้อนหลัง (Tier 9)

## 5. ตัวอย่างเคสทีละขั้น

**อาการ:** "ผู้ใช้ 1 คนเปิดเว็บไม่ได้ แต่คนอื่นได้"
```
 ① ขอบเขต: คนเดียว → ปัญหาที่เครื่อง/พอร์ต/บัญชีของเขา
 ② ipconfig /all → ได้ 169.254.x.x
 ③ สมมติฐาน: ไม่ได้ IP จาก DHCP — สายหลุด / พอร์ตผิด VLAN / พอร์ต err-disabled
 ④ ไฟพอร์ตติด → show interfaces status ที่ switch: พอร์ตอยู่ VLAN 1 แทน VLAN 20
 ⑤ แก้ VLAN ของพอร์ต (ตาม change ที่อนุมัติ/standard change)
 ⑥ ipconfig /renew → ได้ IP ถูก → ผู้ใช้ยืนยันว่าเปิดเว็บได้
 ⑦ บันทึก: ช่างย้ายโต๊ะเมื่อเช้าแล้วเสียบพอร์ตที่ไม่ได้ตั้งค่า → ปรับขั้นตอนการย้ายโต๊ะ
```

**อาการ:** "ทั้งชั้น 5 เข้าเน็ตไม่ได้"
```
 ① ขอบเขต: ทั้งชั้น → อุปกรณ์ที่ใช้ร่วมกัน (access/distribution switch, uplink, VLAN, DHCP)
 ② monitoring: access switch ชั้น 5 ยัง up แต่ uplink ไป distribution down ตั้งแต่ 10:02
 ③ ตรวจ: show interfaces → uplink down/down, SFP rx power ต่ำ
 ④ Swap SFP/patch cord → link up
 ⑤ ยืนยัน + แจ้งผู้ใช้ + เปิด RMA SFP
 ⑦ RCA: uplink ไม่มีเส้นสำรอง → เสนอเพิ่ม uplink ที่ 2 (redundancy)
```

## 6. การสื่อสารระหว่างแก้ปัญหา

- แจ้งผู้ได้รับผลกระทบว่า **รับเรื่องแล้ว** และ **จะอัปเดตครั้งถัดไปเมื่อไร**
- ข้อความอัปเดต: สถานะ · ผลกระทบ · สิ่งที่ทำไปแล้ว · ขั้นต่อไป · เวลาอัปเดตครั้งถัดไป
- อย่าสัญญาเวลาที่ไม่มั่นใจ อย่าโทษบุคคล
- ถ้าเกินความสามารถหรือเกินเวลาที่กำหนด → **escalate** พร้อมข้อมูลที่เก็บไว้

## 7. RCA (Root Cause Analysis)

เขียนหลังเหตุการณ์สำคัญ แบบ **blameless** (มุ่งที่ระบบและกระบวนการ ไม่โทษบุคคล)

**โครงสร้าง RCA**
1. **Summary** — เกิดอะไร สั้น ๆ
2. **Impact** — ใคร/อะไรได้รับผลกระทบ นานเท่าไร
3. **Timeline** — เวลาที่เกิด, ตรวจพบ, ดำเนินการแต่ละขั้น, กลับมาปกติ
4. **Root cause** — สาเหตุที่แท้จริง (ไม่ใช่แค่อาการ)
5. **Resolution** — แก้ชั่วคราวและแก้ถาวร
6. **Action items** — สิ่งที่จะทำเพื่อป้องกันไม่ให้เกิดซ้ำ พร้อมผู้รับผิดชอบและวันที่

### เทคนิค 5 Whys
```
 ปัญหา: อินเทอร์เน็ตล่ม 40 นาที
 Why 1: firewall หลักหยุดทำงาน            → ทำไม?
 Why 2: memory เต็ม                        → ทำไม?
 Why 3: session ค้างจำนวนมากจาก bug ของ firmware → ทำไมยังใช้ firmware นี้?
 Why 4: ไม่มีกระบวนการติดตาม advisory/patch    → ทำไม?
 Why 5: ไม่มีผู้รับผิดชอบ lifecycle ของอุปกรณ์
 Root cause: ขาดกระบวนการจัดการ patch · Action: กำหนดผู้รับผิดชอบ + ตรวจ advisory รายเดือน
 + ทำไม HA ไม่ช่วย? → เครื่องสำรองใช้ firmware เดียวกัน/ไม่ได้ตั้ง monitor memory → เพิ่ม alert
```

## 8. นิสัยของนักแก้ปัญหาที่ดี

- **อย่าเดา — พิสูจน์** ด้วยข้อมูล (log, capture, show)
- **อ่าน error message ให้ครบ** — หลายครั้งบอกคำตอบอยู่แล้ว
- **เปลี่ยนทีละอย่าง** และจดทุกอย่างที่ทำพร้อมเวลา
- **ตรวจสิ่งง่าย ๆ ก่อน** (สายหลุด, พิมพ์ผิด, cert หมดอายุ, DNS)
- **ถาม "มีอะไรเปลี่ยน"** เสมอ
- **ยอมรับเมื่อไม่รู้** และ escalate เร็ว ดีกว่าลองผิดลองถูกนานเกินไป
- **ปิดวงจร:** ทุกปัญหาควรทำให้ระบบหรือเอกสารดีขึ้น

## 9. เรื่องที่คนมักเข้าใจผิด

| ❌ | ✅ |
|---|---|
| reboot แก้ได้ทุกอย่าง | อาจหายชั่วคราวแต่หลักฐานหาย และปัญหากลับมา |
| แก้ได้แล้วไม่ต้องบันทึก | บันทึกช่วยครั้งหน้าและทีมอื่น |
| RCA คือการหาคนผิด | RCA หาจุดอ่อนของระบบ/กระบวนการ (blameless) |
| ping ผ่าน = ผู้ใช้ใช้งานได้ | ต้องให้ผู้ใช้ยืนยันกับงานจริง |


## 11. แบบทดสอบ 10 ข้อ

1. คำถามคัดกรองที่สำคัญที่สุดคืออะไร เพราะอะไร
2. ผู้ใช้คนเดียวมีปัญหา กับทั้งชั้นมีปัญหา บอกอะไรต่างกัน
3. Divide & Conquer เริ่มที่ชั้นใด ทำอย่างไร
4. เมื่อไรควรใช้ Follow-the-path
5. ทำไมต้องเปลี่ยนทีละอย่าง
6. ทำไมควรเก็บหลักฐานก่อน reboot อุปกรณ์
7. Baseline คืออะไร มีประโยชน์อย่างไร
8. องค์ประกอบของ RCA ที่ดีมีอะไรบ้าง
9. 5 Whys ใช้ทำอะไร
10. ข้อความอัปเดตสถานะระหว่างเหตุการณ์ควรมีอะไรบ้าง

<details><summary><b>เฉลย</b></summary>

1. "มีอะไรเปลี่ยนแปลงล่าสุด" — ปัญหาส่วนใหญ่เกิดจากการเปลี่ยนแปลง
2. คนเดียว = ปัญหาน่าจะอยู่ที่เครื่อง/พอร์ต/บัญชีของคนนั้น; ทั้งชั้น = อุปกรณ์/บริการที่ใช้ร่วมกัน (switch, uplink, VLAN, DHCP)
3. L3 — ping ถ้าผ่านไล่ขึ้นชั้นบน ถ้าไม่ผ่านไล่ลงชั้นล่าง
4. ปัญหาที่ข้อมูลต้องผ่านหลายอุปกรณ์/หลายสาขา ไล่ทีละ hop
5. รู้ได้ชัดว่าการเปลี่ยนใดแก้ปัญหา และไม่สร้างปัญหาใหม่ซ้อน
6. reboot ล้าง log/สถานะใน memory ทำให้หา root cause และเปิด case กับ vendor ไม่ได้
7. ค่าปกติของระบบ (bandwidth, CPU, latency, error) ใช้ตัดสินว่าอะไรผิดปกติ
8. Summary, Impact, Timeline, Root cause, Resolution, Action items (ผู้รับผิดชอบ/วันที่) แบบ blameless
9. ถาม "ทำไม" ซ้ำหลายชั้นเพื่อไปให้ถึงสาเหตุที่แท้จริง ไม่หยุดที่อาการ
10. สถานะปัจจุบัน, ผลกระทบ, สิ่งที่ทำไปแล้ว, ขั้นต่อไป, เวลาอัปเดตครั้งถัดไป
</details>
